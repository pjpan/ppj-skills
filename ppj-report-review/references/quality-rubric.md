# Quality Rubric — 管理层汇报的证据与视觉表达

按汇报目的选择证据，不要求每份稿件同时具备所有类型。评审重点是：关键判断是否能被听众快速理解，并有与其强度相称的支撑。

| 类型 | 适用时的合格标准 | 常见误用 |
| --- | --- | --- |
| 价值 | 说明对谁、哪个环节、带来什么变化 | 只有形容词或功能清单 |
| 指标 | 有定义、基线、时间、分母与变化量 | 数字漂亮但口径不明 |
| 数据 | 来源可追溯，图表与结论同口径；观察与因果结论分开 | 把相关性写成因果，截取局部冒充全貌 |
| 机制 | 讲清方案如何产生结果、主要约束和取舍 | 只罗列框架、功能或架构名 |
| 对比 | 对比对象、场景和评价条件可比 | 用不同条件下的数字推断优劣 |
| 案例、访谈或演示 | 具体反馈能说明体验、用法或待验证机制，标明样本与真实、示意或模拟 | 把少量反馈当成效率、经营或普遍效果 |

## 视觉表达优先检查

先圈出整篇最重要的关系、变化和取舍。若用图能让管理层更快理解，评审时指出图要说明的判断、结构和所需证据；重构时按交付格式直接制作图或可渲染图稿，而不是只建议“加一张图”。

| 要表达的问题 | 可选图形 | 必须让读者看见什么 |
| --- | --- | --- |
| 新旧模式或方案差异 | 并列对照图 | 相同维度下的关键变化 |
| 目标如何传导到行动 | 流程图、因果链 | 起点、关键节点、反馈与边界 |
| 多角色或系统如何协作 | 关系图、分层图 | 谁负责什么，信息/任务怎样流动 |
| 效果随时间或条件如何变化 | 趋势图、对照图 | 时间、分组、基线、单位和不确定性 |
| 资源覆盖与优先级 | 矩阵、路线图 | 选择依据、当前状态和下一步 |

图的标题应直接表达主张，标注必须使图能被独立读懂；图旁用一句话写出读图结论。未经验证的因果箭头须改成关联、流程或待验证假设。删去不服务于主张的节点、装饰和动画。图像不能弥补缺失的来源、定义或实验设计；文字更清楚时直接用文字。

## 技术叙事

从业务问题出发，选择解释这个判断真正需要的技术深度：候选方案与取舍、职责边界、关键机制、成本或质量数据。对技术管理者可展示更多实现细节；对经营管理者优先讲机制如何改变结果与风险。公式、伪代码、架构图和演示是工具，不是必填项。

## 交付前追问

- 只看标题和关键图，读者能否理解主要判断及推理路线？
- 每个核心数字是否有定义、时间、分母、来源和可比对象？
- 已验证结果、观察、预测、目标和建议是否清楚分开？
- 若删除某张图，是否会损失关键理解？若不会，考虑删图。
- 下一步是否与汇报目的匹配，责任与检查点是否明确？
