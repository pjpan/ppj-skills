# Quality Rubric — 好汇报的六个要素

一份管理层汇报要同时立住六个面：**价值、指标、数据、技术架构、演示、对比**。任一要素缺失，其余部分的可信度都会被折价。评审时逐项检查，并明确说出缺的是哪一项。

| 要素 | 合格标准 | 典型失败信号 |
|---|---|---|
| **1. 价值** | 第一眼就能看懂值多少：为谁解决什么问题、带来什么改变 | 开篇是活动与功能清单；价值只有形容词（显著提升、大幅优化） |
| **2. 指标** | 收益、效率、质量都有数字，带 baseline 与变化量、统计口径和时间范围 | 只有「提升明显」；有数字但无基线，无法判断增量 |
| **3. 数据** | 图表口径一致、来源可追溯、不做视觉修饰；数据与结论的关系经得起追问 | 图表口径前后不一致；来源缺失；用相关性暗示因果 |
| **4. 技术架构** | 有方法、有架构、有技术密度（关键公式、分层架构图、机制说明） | 只罗列功能与所用框架；没有技术选型的取舍理由 |
| **5. 对比** | 给出明确的对比对象，在同一口径下得出结论 | 没有对比对象，价值自说自话；对比口径与己方不一致 |
| **6. 演示** | 用动画或实机演示直接演出产品价值，降低听众的想象成本 | 用文字描述本可直接演示的效果；演示与讲稿脱节 |

## 价值先行

顺序固定：**先价值，后挑战**。开篇先讲收益、带来的改变、可量化的 baseline 与 breakthrough；困难、风险、资源缺口作为「价值落地路径上待解决的问题」出现在价值之后，不单独占据开头。

原因是管理者的判断从价值出发：开篇先讲困难，判断就停在困难上。自查方式很直接——打开材料第一眼看到的是困难而不是价值，就是写反了。

## 技术叙事

技术部分是说服力的主战场之一，不能只停在「做了哪些功能」。目标是让听众感知到方法深度与工程能力，而不是产品已经能用。

推荐的写法顺序：

1. **问题定义**：技术上真正难的是什么，为什么 naive 方案不够；
2. **方法与选型取舍**：候选方案、选择理由、放弃的方案及原因；
3. **架构分层**：用一张分层架构图交代职责边界与数据流，避免模块罗列；
4. **关键机制**：用公式、伪代码或示意图讲清核心机制，这是「技术密度」的主要来源；
5. **可量化效果**：指标、baseline、测试条件，口径与第 2、3 项要素保持一致；
6. **对照**：与替代方案或业界做法在同一口径下比较。

常见反模式：功能清单式罗列；只讲用了什么框架而不讲为什么；架构图只有模块名没有数据流；用「先进」「领先」替代具体的机制说明。

经验上，一个关键公式 + 一张分层架构图 + 一组同口径指标，比大段文字更能建立技术可信度。

## 六个要素的自检顺序

1. 价值是否第一眼可见（对应「价值先行」）；
2. 每个价值主张是否都有数字与 baseline；
3. 数据口径是否一致、来源是否可追溯；
4. 技术部分是否有机制与架构，而不只是功能；
5. 是否有同口径的对比对象；
6. 是否有可用的演示，或至少说明演示方案。

任何一项只能靠「相信作者」成立时，就直接指出，并给出最小补充项。

## 正例的共同模式

从公认做得好的汇报里反推，两类典型成功组合：

- **价值 + 指标 + 对比 + 技术密度**：价值描述清晰、量化指标丰富、竞品对比夯实、技术部分有公式与机制，听完知道「值多少」，而且这个「多少」是数字。
- **演示 + 价值自解释 + 可信数据 + 充分架构图**：演示动画直观到无需解释，图表数据可信，架构图把技术体系直接呈现出来，技术能力被自然感知。

这两类组合的共同点不是形式，而是**每一项价值主张都有独立的、可核验的支撑**。
