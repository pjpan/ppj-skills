# ppj 汇报评审

将草稿、项目笔记或汇报提纲转化为便于管理层理解与决策的材料。方法上是金字塔原理（结论先行、分层论证）与战略叙事（SCQA）的结合，流程是「先诊断，再重构，最后自检」。

## 输入与任务边界

- 读取用户提供的材料，识别汇报对象、业务目标、项目阶段、期望决策及篇幅要求。信息可合理推断时说明假设；缺失信息会改变结论时，集中提出最关键的问题，并继续处理不依赖答案的部分。
- 没有材料时，请用户提供正文或可读取的文件；若用户要空白模板，直接生成模板。
- 根据请求选择评审、重构或模板模式。默认输出诊断和重构稿；仅要求评审时不扩写全文，仅要求模板时不虚构原稿问题。
- 使用用户指定的语言与交付格式，默认跟随输入语言。本技能不依赖特定平台、联网服务或本地路径；没有文件工具时可直接处理粘贴的正文。

## 核心原则

1. **价值先行。** 顺序固定为先价值、后挑战：开篇落在价值（收益、带来的改变、可量化的 baseline 与突破点），困难、风险与资源缺口作为「价值落地路径上待解决的问题」出现在其后，不单独占据开头。第一眼看到的是困难而不是价值，就是写反了。
2. **结论先行。** 先给结论与所需决策，再展开论据。
3. **MECE。** 同层分类互斥且覆盖当前讨论范围；战略收益不与战术任务混列。
4. **技术是说服力的主战场。** 技术部分要展示方法与架构（关键公式、分层架构图、机制说明），不能停在功能罗列。
5. **论断强度匹配证据强度。** 数量级表述必须由 baseline、口径与数据支撑；证据不足时写成假设并给出验证方式，不默认承诺 10 倍收益。

## 一、诊断逻辑问题

先用四个名字点出典型问题，再逐维检查。每项问题给出原文短引或位置、影响及具体修改建议；区分影响决策的关键问题与表达优化，不为凑数制造问题。

| 典型问题 | 表现 |
| --- | --- |
| 自嗨式汇报 | 一上来就是「我们做了 X、Y、Z」，没有业务背景（S）与关键矛盾（C） |
| 逻辑层级混乱 | 同一条列表里混放战略收益与战术任务（非 MECE） |
| 空中楼阁 | 直接提出宏大平台/战略，没有经过验证的 MVP 或快速见效的局部 |
| 逻辑断层 | 章节之间没有时间（过去/现在/未来）或角色（一线→中层→总部）上的递进 |

逐维检查：

| 维度 | 检查重点 |
| --- | --- |
| 业务价值 | 开头是否只列做了什么？是否说明为谁解决什么问题、为什么值得投入？ |
| 结论与层级 | 是否结论先行？同层条目是否使用同一分类标准？是否把战略收益与功能任务混列？ |
| 分类完整性 | 尽量做到 MECE，即分类不重叠且覆盖当前讨论范围；不强行凑三个维度。 |
| 证据与因果 | 收益是否有来源、基线、统计口径和时间范围？是否把相关性写成因果、将目标写成成果？价值主张是否有同口径的对比对象？ |
| 优先级与验证 | 为什么先选这个场景？是否说明可行性、验证成本、代表性和成功标准？宏大推广计划是否缺少局部验证？ |
| 执行与决策 | 交付物、里程碑、责任方、依赖、风险和资源诉求是否足以支持下一步决策？ |
| 叙事衔接 | 章节间是否有因果、时间或角色递进？是否出现没有论据支撑的跳跃？ |
| 技术叙事 | 技术部分是否有方法、架构与技术密度，而不只是功能清单与框架名称？ |

事实约束：保留原材料的数字、单位、日期和限定条件；区分已验证事实、用户目标、推断与待验证假设。缺失信息用「待补充」并说明需补什么证据，不编造客户、数据、试点成果、承诺或来源。

## 二、重构汇报

先用一至三句话交代核心结论、证据与希望获得的决策。默认用下列四阶段组织正文；用户已有强制模板时，将内容映射到该模板。按项目阶段缩减不适用部分，不把日常进展汇报强行扩成平台战略。

| 阶段 | 应回答的问题 | 应呈现的内容 |
| --- | --- | --- |
| 1. 战略愿景与核心价值（Why） | 为什么现在做？业务价值是什么？ | 结论先行给出突破性价值，再做 MECE 价值拆解（规模/数量、精度/质量、速度/效率）；用 SCQA 串联现状（S）、矛盾（C）、关键问题（Q）与回答（A），给出基线与口径。 |
| 2. 战略聚焦与 MVP 验证（Where / How） | 为什么先做这里？如何判断有效？ | 场景选择理由（可行性、验证成本、代表性、杠杆）、最小可行方案（MVP）、试点数据与局限；未验证时写实验范围、指标、成功阈值与下一步。 |
| 3. 产品化与规模化推广（What） | 交付什么？给谁用？何时落地？ | 按角色或业务环节组织方案矩阵；时间明确、可检查的里程碑（Alpha/Beta/GA）；明确从试点进入推广的条件。 |
| 4. 未来扩展与行动诉求（Next） | 需要谁决定什么？下一步如何推进？ | 能力横向复制到其他业务线的路径与前提；具体的资源、支持方、决策事项、时间要求与检查点。 |

需要完整的四阶段写法、四类问题的详述、一页纸模板或「零散笔记重组步骤」时，读 [references/executive-blueprint.md](references/executive-blueprint.md)。

## 三、按六要素验收

重构完成后，逐项检查汇报是否同时立住六个面：**价值、指标、数据、技术架构、演示、对比**。任一要素缺失，其余部分的可信度都会被折价。

| 要素 | 合格标准 |
| --- | --- |
| 价值 | 第一眼就能看懂值多少：为谁解决什么问题、带来什么改变 |
| 指标 | 收益、效率、质量都有数字，带 baseline 与变化量、统计口径、时间范围 |
| 数据 | 图表口径一致、来源可追溯、不做修饰 |
| 技术架构 | 有方法、有架构、有技术密度（公式、分层架构图、机制说明） |
| 对比 | 有明确的对比对象，并在同一口径下给出结论 |
| 演示 | 用动画或实机演示直接演出产品价值，降低理解成本 |

需要各要素的失败信号、技术叙事的推荐写法与正例模式时，读 [references/quality-rubric.md](references/quality-rubric.md)。

## 四、默认输出

### 1. 🚨 汇报评审：逻辑与证据漏洞

按重要性列出「原文依据 → 问题及影响 → 修改建议」。先按典型问题命名（自嗨式、逻辑层级混乱、空中楼阁、逻辑断层），再展开。材料足够好时明确指出，无须强行批评。

### 2. 📊 重构后的汇报

提供已填入现有事实的四阶段框架表，或用户指定格式的可直接使用稿。保留必要的「待补充」标记；不要只返回抽象写作建议。

### 3. 💡 叙事改进与待补信息

给出两至三条针对当前材料的表达建议；如果缺少影响决策的证据，列出最少且关键的补充项。建议与事实分开表述。

## 交付前自检

- **So What**：开头能否让读者知道业务价值与所需决策？价值是否先于挑战出现？
- **Why This**：起点选择是否有依据，验证方案是否能支持下一步？
- **MECE**：同层分类是否一致，是否混淆战略价值与执行任务？
- **事实**：是否把愿景写成结果，或新增了无来源的数字和承诺？
- **六要素**：价值、指标、数据、技术架构、对比、演示是否都有支撑，还是只能靠「相信作者」？
- **可行动**：读者是否知道谁需要做什么、何时检查，以及还缺什么证据？

直接修正检查中发现的问题，再交付最终稿；用户未要求时，不输出内部自检过程。
