# ppj 汇报评审

将草稿、项目笔记或汇报提纲转化为便于管理层理解、讨论与决策的材料。先识别汇报意图，再诊断、重构和自检；金字塔原理与 SCQA 是可选工具，不是必须套用的格式。

## 输入与任务边界

- 读取用户提供的材料，识别汇报对象、业务目标、项目阶段、汇报意图（对齐方向、展示成果、争取决策或例行同步）及篇幅要求。信息可合理推断时说明假设；缺失信息会改变结论时，集中提出最关键的问题，并继续处理不依赖答案的部分。
- 没有材料时，请用户提供正文或可读取的文件；若用户要空白模板，直接生成模板。
- 按用户要求选择交付模式：要求“评审、审查、找问题”时只给诊断和修改建议；要求“修改、重构、形成可用稿”时交付改稿，并简述关键改动；没有原稿且要求模板时交付可填写的框架。用户同时要求评审和改稿时两者都给。未明确要求改稿时，不自动扩写全文。
- 使用用户指定的语言与交付格式，默认跟随输入语言。本技能不依赖特定平台、联网服务或本地路径；没有文件工具时可直接处理粘贴的正文。

## 核心原则

1. **开篇交代汇报意图。** 让管理层尽快知道本次要理解、讨论或决定什么，以及它与业务的关系。可以从判断、机会、进展、风险或待决问题起笔；以最能帮助当前听众理解的切口为准。
2. **一条主线贯穿全篇。** 先确定听众最需要回答的问题，再安排背景、证据、方案和下一步。每章有明确任务，前后有合理递进；不固定章节数量、顺序或叙事模型。
3. **成果与规划分层。** 已上线、使用、业务效果、能力成熟度、未来目标、估算预测分别标注。访谈和案例可支持具体体验或用法的判断；使用量说明采用；同口径结果数据可支持观察到的变化；因果或推广效果需相应的对照、实验设计与适用范围。不同层证据不能互相替代。
4. **用听众能判断的语言讲专业内容。** 解释方案、技术或流程如何影响业务目标及关键约束；按听众和议题选择机制、成本、质量、稳定性、治理等证据。类比、图示、公式和架构图只在能降低理解成本时使用。
5. **优先让关键逻辑可视化。** 对新旧模式、关系、能力分层、推进路径和方案取舍，先考虑能否用图清楚表达核心观点。评审模式给出图要证明的判断、结构与所需证据；重构模式在适合用图且交付格式支持时，直接提供可插入的图或可渲染图稿。图须有观点式标题、明确的对象与连线/坐标含义、必要的口径和一句读图结论；未经验证的关系标为假设或示意，不画成已证实的因果。文字更清楚时直接用文字。
6. **论断强度匹配证据强度。** 数量级与因果表述须有基线、口径、时间、样本或实验设计支撑；预测写清输入假设。结论不成立时直接降级措辞并给出验证办法。
7. **以符合汇报目的的下一步收束。** 方向对齐稿说明待验证判断和共识形成方式；进展稿说明下一检查点；决策稿说明选项、建议与所需决定。远期暂无可信量化目标时，坦诚标出不确定性。

具体写法应以用户的汇报目的、听众和现有材料为准。需要借鉴方向对齐类汇报的表达形式时，可读[管理层汇报的形式观察](references/executive-report-example.md)；它只提供可选方法，不是固定模板。

## 一、诊断逻辑问题

先识别真正影响理解或决策的问题；可借用下表的名字，勿强行凑齐四类。每项问题给出原文短引或位置、影响及具体修改建议；区分关键问题与表达优化。

| 典型问题 | 表现 |
| --- | --- |
| 自嗨式汇报 | 一上来就是「我们做了 X、Y、Z」，没有业务背景（S）与关键矛盾（C） |
| 逻辑层级混乱 | 同一条列表里混放战略收益与战术任务（非 MECE） |
| 空中楼阁 | 直接提出宏大平台/战略，没有经过验证的 MVP 或快速见效的局部 |
| 逻辑断层 | 章节之间没有时间（过去/现在/未来）或角色（一线→中层→总部）上的递进 |

逐维检查：

| 维度 | 检查重点 |
| --- | --- |
| 汇报意图与主线 | 开篇能否看懂这次要理解、讨论或决定什么？各部分是否服务于同一个关键问题？ |
| 核心信息与层级 | 读者能否快速找到本次最重要的信息？同层条目是否使用同一分类标准？是否把战略收益与功能任务混列？ |
| 分类完整性 | 尽量做到 MECE，即分类不重叠且覆盖当前讨论范围；不强行凑三个维度。 |
| 证据与因果 | 收益是否有来源、基线、统计口径和时间范围？是否把相关性写成因果、将目标写成成果？价值主张是否有同口径的对比对象？ |
| 优先级与验证 | 为什么先选这个场景？是否说明可行性、验证成本、代表性和成功标准？宏大推广计划是否缺少局部验证？ |
| 执行与决策 | 近期目标、衡量方式、责任方、依赖和风险是否可追踪？需要决策时，决策事项是否具体？ |
| 叙事衔接 | 章节间是否有因果、时间或角色递进？是否出现没有论据支撑的跳跃？ |
| 视觉表达 | 核心关系与变化是否能由图直接看懂？图有明确观点、图例/口径和读图结论吗？是否存在装饰图或一图承载太多观点？ |
| 技术叙事 | 技术方法是否解释业务收益或关键约束？必要的成本、质量、稳定性与治理证据是否到位？ |

事实约束：保留原材料的数字、单位、日期和限定条件；区分已验证事实、用户目标、推断与待验证假设。缺失信息用「待补充」并说明需补什么证据，不编造客户、数据、试点成果、承诺或来源。

## 二、重构汇报

开篇简要交代汇报目的、当前判断与最关键的依据。根据实际任务选择结构；下表只是整理材料时可参考的问题清单，可重排、合并或省略。

| 内容块 | 应回答的问题 | 应呈现的内容 |
| --- | --- | --- |
| 背景与判断 | 为什么这件事值得管理层关注？ | 说明业务对象、当前变化及其影响；必要时给出基线或关键矛盾。 |
| 实践与证据 | 已知什么，仍未知什么？ | 用与论点相称的案例、数据、对照或试验；注明范围、时间和局限。 |
| 方案与能力 | 结果如何产生、维持或改进？ | 讲清关键机制、取舍与约束；按议题选择技术、组织或执行细节。 |
| 后续与决策 | 听众接下来需要做什么？ | 根据目的写检查点、待验证问题、资源依赖或决策选项。 |

需要战略型汇报的详细写法、一页纸模板或「零散笔记重组步骤」时，读 [references/executive-blueprint.md](references/executive-blueprint.md)。

## 三、按证据需求验收

重构完成后，按汇报目的检查六类可用证据：**价值、指标、数据、技术机制、演示、对比**。不是每份材料都必须六项齐全；选能支撑关键判断的证据，并指出缺失哪项会影响决策。

| 要素 | 合格标准 |
| --- | --- |
| 价值 | 读者能看懂为谁解决什么问题、带来什么改变；可量化时说明幅度 |
| 指标 | 关键指标有定义、基线、变化量、统计口径和时间范围；暂无数据时说明验证方式 |
| 数据 | 图表口径一致、来源可追溯，视觉编码不夸大差异 |
| 技术机制 | 有必要的方法、架构或机制，能解释关键业务收益与约束 |
| 对比 | 有明确的对比对象，并在同一口径下给出结论 |
| 演示 | 适用时用真实案例、产品截图或实机演示呈现价值；标明示意与真实使用 |

需要各要素的失败信号、技术叙事的推荐写法与正例模式时，读 [references/quality-rubric.md](references/quality-rubric.md)。

## 四、按任务模式交付

| 模式 | 交付物 |
| --- | --- |
| 评审 | 按影响程度列出「原文依据 → 问题及影响 → 修改建议」，并指出最关键的待补证据。适合可视化时，给具体图稿建议；不重写全文。 |
| 重构 | 给可直接使用的改稿，简述关键改动。适合可视化且格式支持时，提供实际图或可渲染图稿；资料不足时保留「待补充」标记。 |
| 模板 | 给与汇报目的相符的可填写框架，不假设已有问题或虚构事实。 |

用户同时要求多种模式时组合相应交付物。用用户指定的格式，不强加标题、表格或表情符号。

对现有稿件提出建议时，适用才借用典型问题命名；材料足够好时明确指出，无须强行批评。建议与事实分开表述，不只返回抽象写作建议。

## 交付前自检

- **So What**：开头能否让读者知道本次讨论目的，以及最值得关注的业务判断、进展或问题？
- **Why This**：起点选择是否有依据，验证方案是否能支持下一步？
- **MECE**：同层分类是否一致，是否混淆战略价值与执行任务？
- **事实**：是否把愿景写成结果，或新增了无来源的数字和承诺？
- **方案档位与实测范围**：涉及多参数规模或多版本方案时，逐一核对标题、正文和图中的规划档位；单一档位的实验结果只标为该档已验证，不写成整个方案的结论。
- **证据链**：案例、使用、效果、能力和预测是否分层，同口径比较是否成立？关键判断是否只能靠「相信作者」？
- **图像表达**：关键关系和变化是否能通过图直接理解？标题、标注、来源和读图结论是否完整？
- **可行动**：读者是否知道近期目标、谁来推进、何时检查；需要决策时，选项和诉求是否清楚？

直接修正检查中发现的问题，再交付最终稿；用户未要求时，不输出内部自检过程。
