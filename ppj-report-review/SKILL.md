# ppj汇报评审skills

将草稿、项目笔记或汇报提纲转化为便于管理层理解与决策的材料。结合金字塔原理（结论先行、分层论证）与战略叙事，先诊断，再重构，最后自检。

## 输入与任务边界

- 读取用户提供的材料，识别汇报对象、业务目标、项目阶段、期望决策及篇幅要求。信息可合理推断时说明假设；缺失信息会改变结论时，集中提出最关键的问题，并继续处理不依赖答案的部分。
- 没有材料时，请用户提供正文或可读取的文件；若用户要空白模板，直接生成模板。
- 根据请求选择评审、重构或模板模式。默认输出诊断和重构稿；仅要求评审时不扩写全文，仅要求模板时不虚构原稿问题。
- 使用用户指定的语言与交付格式，默认跟随输入语言。本技能不依赖特定平台、联网服务或本地路径；没有文件工具时可直接处理粘贴的正文。

## 一、诊断逻辑问题

围绕下列维度检查实际存在的问题；每项问题给出原文短引或位置、影响及具体修改建议。区分影响决策的关键问题与表达优化，不为凑数制造问题。

| 维度 | 检查重点 |
| --- | --- |
| 业务价值 | 开头是否只列做了什么？是否说明为谁解决什么问题、为什么值得投入？ |
| 结论与层级 | 是否结论先行？同层条目是否使用同一分类标准？是否把战略收益与功能任务混列？ |
| 分类完整性 | 尽量做到 MECE，即分类不重叠且覆盖当前讨论范围；不强行凑三个维度。 |
| 证据与因果 | 收益是否有来源、基线、统计口径和时间范围？是否把相关性写成因果、将目标写成成果？ |
| 优先级与验证 | 为什么先选这个场景？是否说明可行性、验证成本、代表性和成功标准？宏大推广计划是否缺少局部验证？ |
| 执行与决策 | 交付物、里程碑、责任方、依赖、风险和资源诉求是否足以支持下一步决策？ |
| 叙事衔接 | 章节间是否有因果、时间或角色递进？是否出现没有论据支撑的跳跃？ |

事实约束：保留原材料的数字、单位、日期和限定条件；区分已验证事实、用户目标、推断与待验证假设。缺失信息用“待补充”并说明需补什么证据，不编造客户、数据、试点成果、承诺或来源。不默认承诺 10 倍收益；尚无试点时给出验证计划。

## 二、重构汇报

先用一至三句话交代核心结论、证据与希望获得的决策。默认用下列四阶段组织正文；用户已有强制模板时，将内容映射到该模板。按项目阶段缩减不适用部分，不把日常进展汇报强行扩成平台战略。

| 阶段 | 应回答的问题 | 应呈现的内容 |
| --- | --- | --- |
| 1. 背景与核心价值（Why） | 为什么现在做？业务价值是什么？ | 用 SCQA 串联现状（S）、矛盾（C）、关键问题（Q）与回答（A）；给出基线与价值维度。可以用 SCQA 构思，再以结论先行的顺序呈现。 |
| 2. 聚焦场景与验证（Where / How） | 为什么先做这里？如何判断有效？ | 场景选择理由、最小可行方案（MVP）、试点证据及局限；未验证时写实验范围、指标、成功阈值与下一步。 |
| 3. 交付与推广（What） | 交付什么？给谁用？何时落地？ | 按用户角色或业务环节组织方案，列里程碑、责任、依赖与风险；明确从试点进入推广的条件。 |
| 4. 后续行动与决策诉求（Next） | 需要谁决定什么？下一步如何推进？ | 明确资源、支持方、决策事项、时间要求与后续检查点；有证据时说明复制路径。 |

## 三、默认输出

### 1. 汇报评审：主要问题

按重要性列出“原文依据 → 问题及影响 → 修改建议”。材料足够好时明确指出，无须强行批评。

### 2. 重构后的汇报

提供已填入现有事实的四阶段框架表，或用户指定格式的可直接使用稿。保留必要的“待补充”标记；不要只返回抽象写作建议。

### 3. 叙事改进与待补信息

给出两至三条针对当前材料的表达建议；如果缺少影响决策的证据，列出最少且关键的补充项。建议与事实分开表述。

## 交付前自检

- So What：开头能否让读者知道业务价值与所需决策？
- Why This：起点选择是否有依据，验证方案是否能支持下一步？
- MECE：同层分类是否一致，是否混淆战略价值与执行任务？
- 事实：是否把愿景写成结果，或新增了无来源的数字和承诺？
- 可行动：读者是否知道谁需要做什么、何时检查，以及还缺什么证据？

直接修正检查中发现的问题，再交付最终稿；用户未要求时，不输出内部自检过程。
